nexuiz — Nexuiz Classic 2.5.2 on the DarkPlaces engine, in the room
====================================================================

WHAT THIS IS
------------
The real game. The client is the DarkPlaces engine compiled from its
real source tree to WebAssembly; the data is the original Nexuiz
2.5.2 release data, byte-for-byte; the game logic is the game's own
QuakeC progs. One progs file carries a tracked house patch: the
menu (see HOUSE MENU OVERRIDE below). Nothing here is a
re-implementation.

HOW THE DATA TRAVELS
--------------------
The packs are too large to ship as site files, and no lawful upstream
sends the CORS headers a browser fetch would need (measured
2026-10-25). The site's data pipe (/api/nexuiz-data) therefore
streams fixed 16 MiB chunks of each pack's raw-deflate span inside
the pinned release zip:

  data20091001.pk3 span: bytes [23842145, 904335770) of nexuiz-252.zip
  common-spog.pk3  span: bytes [904335848, 904360486) of nexuiz-252.zip

The loader inflates the span, reassembles the pack, and verifies the
SHA-256 above before the engine starts. Wrong bytes are refused.
Chunks are cached by the browser (Cache API) so the wire is crossed
once. License for the game data and code: GPL-2.0 (the release's own
terms; see COPYING.txt).

HOUSE CONFIGURATION (the only deliberate deviation from stock)
--------------------------------------------------------------
public/nexuiz/autoexec.cfg — cvars only, the way real servers were
configured. It makes local games MinstaHook instagib (g_minstagib 1,
g_grappling_hook 1 — the "thisissparta" flavor) with the era's
tunings. The house server is named thisissparta2! — it runs natively
at the house, and its public bridge address is published (it is
the constant the OS window deals with the game frame). The game
boots to its own main menu; the room's door stands in that menu,
and entering the room is the player's own press there — no
connection is ever made for the player at boot.
Bots are a switch, never a condition of the room: the local
match's toggle sets bot_number at the table; the house room's fill
is the host's server-side switch (bot_join_empty / minplayers).

HOUSE MENU OVERRIDE — SETTINGS LOCKED, THE ROOM'S DOOR IN THE MENU
--------------------------------------------------------------
Every player here runs the same build specs and configs (the house
configuration above is dealt to everyone identically), so the
in-game Settings are locked: they open on a single Player page
whose only working control is the player NAME field. Video,
effects, audio, input, network and misc settings cannot be
changed from the menu; neither can model, skin, colors, crosshair
or view settings — the Multiplayer dialog's Player Setup tab is
the same surface and is locked the same way. The name field works
exactly as stock (type, Apply, and that name is the one you wear
in the room).

The same override carries the room's front door: the game boots
to its main menu, and at the head of the Multiplayer dialog —
above the server browser — stands a button labeled
"thisissparta2!", a stock command button whose command is
"connect thisissparta2": the very connect the boot used to deal
sight unseen, now pressed by the player's own hand. It is the
same road, not a new one — the engine's socket layer dials the
dealt bridge address for any connect (the shipped glue's peer
construction takes the dealt URL whole), so the door and the
retired auto-join differ only in whose hand presses. The
Singleplayer dialog and the stock server browser are untouched
and work as shipped.

Mechanism: the override pack public/nexuiz/sparta-menu.pk3
(160,556 bytes, one entry: menu.dat) rides in the game directory
beside the release packs; the engine's own directory order makes
its menu.dat the one that loads — the same route as the house
room's sparta-progs / sparta-csprogs overrides. Nothing in the
release packs is modified.

  sparta-menu.pk3  SHA-256 1ecf5d09ff61c5b614685dfe7d66710b0484272b22b159db1e8ac031d8c1435a
  menu.dat inside  SHA-256 2444a040d1780cc7f960918c2e2db989cd745357ba658a8b00179e8b5acb9a53

The menu.dat is compiled from the release's own menu sources
(qcsrc/menu in gamesource20091001.zip) with the era's own fteqcc
(the rev1253299209 binary the release archive ships), flags
-O1 -Oreturn_only -Ostrip_functions, plus the tracked patches —
tools/nexuiz/house-qc-patch-008.diff (three files) and, stacked
on it, tools/nexuiz/house-qc-patch-009.diff (one file):

  dialog_settings.c: the Settings dialog's six tabs (Input,
    Video, Effects, Audio, Network, Misc) are replaced by the
    single Player tab, and the dialog takes the same 24-row
    height as the Multiplayer dialog — a tab's declared height
    must equal its controller's, and the shared player tab is
    a 22-row tab.
  dialog_multiplayer_playersetup.c: the player tab keeps only
    the name label, the name field and the stock "Apply
    immediately" row (the apply command is byte-for-byte the
    stock one). Everything the
    tab used to offer below the name — color picker, charmap,
    model selector, shirt/pants colors, field of view, view
    bobbing, zoom, weapon settings, crosshair, radar/HUD,
    gore — is removed, and with it the only doors to the
    weapons, radar and advanced-cvars dialogs.
  menu.qc: the main menu draws the build's tag — "rezzmodV1",
    etched in red (a dark groove pass, a lit top edge, the red
    face) at the lower right of the title area, the treatment
    the native build's menu plate carries. Drawn with the menu
    background, under every dialog; the in-game menu background
    stays stock, as on the native build. The version tag lives
    here, in the game — not on the site around it.
  dialog_multiplayer.c (patch 009): the Multiplayer dialog
    gains the room's door — a full-width stock command button
    labeled "thisissparta2!" at its head, issuing
    "connect thisissparta2" with no close flag, exactly as the
    stock server browser's own Join does. The dialog grows one
    row (24 to 25) and its tab controller's height drops the
    same row, so the controller stays level with its four
    22-row tabs. The door carries no name dependency, unlike
    the stock tabs below it: the web build deals the player's
    name to the engine itself, and the cvar those tabs gate on
    is only the menu's staging name — gating the door on it
    would bar the dealt-name player it serves.

Parity of the base build, stated exactly: rebuilt from the
unmodified sources, the menu program's header CRC is 10020 —
the shipped menu.dat's own CRC — and its strings, field
definitions, global definitions and initial global data are
byte-identical to the shipped file's, as is the function table's
shape (1,010 functions, same names, order and parameter
metadata). The compiled statement streams differ in 168 of
1,010 functions, only in how function exits are encoded
(direct DONE/RETURN terminators versus jumps to a shared exit —
the opcode census of the differing functions is confined to
DONE, RETURN, IF, IFNOT and GOTO); the release was compiled
with an fteqcc revision two weeks younger than the one the
archive bundles, which does not survive, so byte-identity of
the code section is not claimed. What is claimed: same defs,
same strings, same globals, same CRC — and the same behavior,
driven and screenshotted against the real client.

Parity of patch 009 against the patch-008 build, measured the
same way: header CRC still 10020; 1,010 functions, same names
and order; field definitions identical; exactly one function's
statement stream changes — fillNexuizMultiplayerDialog, 91 to
107 statements (+16, the net program delta) — plus the global
renumbering two new anonymous string globals cause (the door's
label and its command; every other stream shift is that
renumbering, not new code).

One honest limit: this lock governs the menu surface. The
engine's developer console — a stock part of the game — can
still set cvars directly, as it could for any player of the
original release. Sealing it would take an engine change, and
none is made here.

NETWORKING, HONESTLY
--------------------
DarkPlaces speaks UDP (lhnet.c, stock). A browser has no UDP: the
engine's socket layer (Emscripten SOCKFS) dials a WebSocket address
verbatim, and the house bridge (sparta-bridge) carries each binary
frame as one datagram to the real server — one WebSocket session is
one player. The bridge's public address is dealt with the game
frame as a standing transport (the "sparta" subprotocol; a WebRTC
DataChannel is tried first on the same door, every failure landing
on the WebSocket — see play.js). It dials nothing on its own: the
socket opens when the player takes the menu's door, or makes any
connect of their own. Local play needs none of it: menus, the
single-player ladder, and bot matches run on the engine's own
in-process server.
