nexuiz — Nexuiz Classic 2.5.2 on the DarkPlaces engine, in the room
====================================================================

WHAT THIS IS
------------
The real game. The client is the DarkPlaces engine compiled from its
real source tree to WebAssembly; the data is the original Nexuiz
2.5.2 release data, byte-for-byte; the game logic is the game's own
QuakeC progs. One progs file carries a tracked house patch: the
menu (see HOUSE MENU OVERRIDE below). Nothing here is a
re-implementation.

WHAT IS SERVED — THE HAXIUZ STRIPPED PACK
-----------------------------------------
haxiuz plays one session — CTF MinstaHook on evilspace — so the
site no longer ships the release's whole data universe. It serves
one house-built pack containing only what that session loads:

  data/haxiuz.pk3 — 99,228,456 bytes, 1,528 files
    SHA-256 10018c6a19fee310c70504952691fb21748ff5d1412c4f1271ff7de658d7f5b3

Every file in it is a byte-for-byte member of the verified source
packs above (common-spog's files ride inside it); nothing is
re-encoded, resized or renamed. Its contents are a measured
census, not a guess: the real client was run against the full
data (menu, and a full bot match on evilspace under the house
rules) with every file open recorded, and the pack is that
record, closed out with the companions the engine loads beside
what it opens (model skins and frame groups, texture variant
sets, randomized sound variants, the item models and their
textures, and every player model — the gamecode precaches them
all at match start, qcsrc/server/miscfunctions.qc). The pack was
then played the same way and its console censused against the
full data's: no file a session reaches for is missing from it.
What is NOT in it is everything a session never loads: the other
maps and their textures, the other weapons, modes, vehicles and
turrets, the campaign and demo data, and all but the two music
tracks the menu and evilspace play. The full account — file
counts, byte accounting by category, and how to restore the
full-data deal if a miss ever surfaces — is in
tools/nexuiz/BUILD.md.

HOW THE DATA TRAVELS
--------------------
The stripped pack travels the site's span pipe
(/api/nexuiz-data), the road the release packs took before it:
at 99 MB the pack is far past the 25 MiB ceiling on a site file,
so it cannot ride as one. The pipe streams fixed 16 MiB chunks
of the pack's raw-deflate span inside its container zip; the
loader inflates the span, reassembles the pack byte-for-byte,
and verifies its SHA-256 against the pin above before the
engine starts — wrong bytes are refused, never played. The
verified pack is then kept on the player's machine, so the wire
is crossed once.

The container is a house-built zip whose single deflated entry
is the pack itself, published as a release asset on the
house's haxiuz repo (github.com/nightwarelabz/haxiuz, release
tag data-1):

  haxiuz-release.zip — 98,509,335 bytes
    SHA-256 f00dc045337d245bc3be901763d1fe7607112f383bc64abcc9611f33f8a252f1
    the pack's span inside it: offset 40, length 98,509,217

The site's build verification checks that the frame's deal of
the pack — its pipe part, its span, and its hash pin — is what
the site ships. The full-data deal the pipe carried before
(parts "data" and "spog", spans of the release zip above)
stands as the documented restore; it is written down in
tools/nexuiz/BUILD.md. License for the game data and code:
GPL-2.0 (the release's own terms; see COPYING.txt).

HOUSE CONFIGURATION (the only deliberate deviation from stock)
--------------------------------------------------------------
public/nexuiz/autoexec.cfg — cvars only, the way real servers were
configured. It makes local games MinstaHook instagib (g_minstagib 1,
g_grappling_hook 1 — the "thisissparta" flavor) with the era's
tunings. The house server is named thisissparta2! — it runs natively
at the house, and its public bridge address is published (it is
the constant the OS window deals with the game frame). The game
boots to its own main menu; the room's door stands in that menu,
and entering the room is the player's own press there — no
connection is ever made for the player at boot.
Bots are a switch, never a condition of the room: the local
match's toggle sets bot_number at the table; the house room's fill
is the host's server-side switch (bot_join_empty / minplayers).

HOUSE MENU OVERRIDE — SETTINGS LOCKED, THE ROOM'S DOOR IN THE MENU
--------------------------------------------------------------
Every player here runs the same build specs and configs (the house
configuration above is dealt to everyone identically), so the
in-game Settings are locked: they open on a single Player page
whose only working control is the player NAME field. Video,
effects, audio, input, network and misc settings cannot be
changed from the menu; neither can model, skin, colors, crosshair
or view settings — the Multiplayer dialog's Player Setup tab is
the same surface and is locked the same way. The name field works
exactly as stock (type, Apply, and that name is the one you wear
in the room).

The same override carries the room's front door: the game boots
to its main menu, and at the head of the Multiplayer dialog —
above the server browser — stands a button labeled
"haxiuz", a stock command button whose command is
"connect thisissparta2": the very connect the boot used to deal
sight unseen, now pressed by the player's own hand. It is the
same road, not a new one — the engine's socket layer dials the
dealt bridge address for any connect (the shipped glue's peer
construction takes the dealt URL whole), so the door and the
retired auto-join differ only in whose hand presses. The
Singleplayer dialog and the stock server browser are untouched
and work as shipped.

Mechanism: the override pack public/nexuiz/sparta-menu.pk3
(160,520 bytes, one entry: menu.dat) rides in the game directory
beside the release packs; the engine's own directory order makes
its menu.dat the one that loads — the same route as the house
room's sparta-progs / sparta-csprogs overrides. Nothing in the
release packs is modified.

NETWORKING, HONESTLY
--------------------
DarkPlaces speaks UDP (lhnet.c, stock). A browser has no UDP: the
engine's socket layer (Emscripten SOCKFS) dials a WebSocket address
verbatim, and the house bridge (sparta-bridge) carries each binary
frame as one datagram to the real server — one WebSocket session is
one player. The bridge's public address is dealt with the game
frame as a standing transport (the "sparta" subprotocol; a WebRTC
DataChannel is tried first on the same door, every failure landing
on the WebSocket — see play.js). It dials nothing on its own: the
socket opens when the player takes the menu's door, or makes any
connect of their own. Local play needs none of it: menus, the
single-player ladder, and bot matches run on the engine's own
in-process server.

SESSION DIAGNOSTICS (OPT-IN, OFF BY DEFAULT)
--------------------------------------------
The play frame and its OS window carry a diagnostics layer that
is off unless the operator arms it (a local-storage flag read by
the OS window, or the page query word nexuiz-diag=1). Unarmed,
nothing is sampled, no statistics are read, and no panel stands.
Armed for a deal, the window mints a session tag the frame echoes
on every message; the frame then samples its own session every
500 ms into a bounded history (1,200 samples, 200 events) and the
window's panel shows the running account, with an export of the
whole record as JSON on request.

What it reads, and only that: the session's own connection. The
socket shim keeps the engine's sockets in a registry while armed,
and the sampler reads the active one — which transport carried
the session (WebRTC or the WebSocket fallback), why the fast road
did not carry it when it did not, the setup time, the frame and
byte counters, and the outgoing buffered amount. For a WebRTC
carriage it also reads the ACTIVE peer connection's own
statistics (the selected candidate pair, its candidate types and
protocols, its round-trip time). No second peer is ever opened
to measure. Two frame signals are kept apart on purpose: page
animation-frame intervals (the browser's scheduling of the page,
with a baseline frozen from before the engine started) and the
engine's own main-loop iterations, counted from the engine
glue's frame counter, which is reached only through an
own-property descriptor probe — the standing rule for this glue,
whose unexported runtime names abort on a direct read. The
engine and the game data are untouched by all of it: no engine
rebuild, no stamp change, no configuration change.
